# 预登记门禁设计

门禁（gate）= 实验开跑前写死的判据。它的价值有两面：防事后调阈值，也防事前提前宣布结论。
七题实战里，主动弃投的候选数量超过实际投出的，这是纪律在起作用，不是保守。

## 1. 预登记内容（缺一不可）

| 项 | 要求 |
|---|---|
| 对照臂 | 唯一线上验证过的锚点（不是「上一个离线最好」）；对照与候选同口径 |
| 唯一变量 | 一句话写清，其余全部冻结（含推理设置、设备、后处理） |
| 主门阈值 | 用单步分辨率换算（≥ 3 步），不拍整数 |
| 否决门 | 代价侧不得恶化超过 1 个等效实例（见 §3） |
| 暴露度门 | 相对线上锚点 ≥ 门槛 |
| 口径 | 权重（冻结 / 重搜）、设备、dev 集、TTA、后处理 |
| 无缝处置表 | 穷举所有结果区间，每段写处置 + 不做什么（见 §2） |
| 资源门 | 显存 / 内存峰值预算、smoke 步数、超时；不满足则不判定、不降 batch |

用 `/comp-gate` 命令写进 experiment-log；也可写进 receipt JSON（比文档更难事后改）。

## 2. 判据无缝覆盖，每段写明「不做什么」

有缝的判据等于没有判据：`<88.7 回退 / [缝] / 89.1~89.3 关闭 / [缝] / ≥89.5 成立`——
缝隙恰恰是最可能落的区间，也最容易被说成「接近 89.5，算成立吧」。

补齐后的五段示例：

| 结果 | 处置 |
|---|---|
| 主门过 + 否决门过 + 归因相符 | **提交**（唯一该投的情形） |
| 主门过、否决门不过 | 不投，判「换包装」，**不变体化** |
| 主门不过、目标类正向 | 不投，记「机理成立幅度不足」，保留结论不保留候选 |
| 两者都不过 | 不投，**方向关闭**，不改注入位置 / 不加强度旋钮 / 不回试已否定档位 |
| 未跑满 / OOM | 不判定；**不降 batch**（同时改 BN 统计与有效 LR） |

最差区间要预设**诊断分支**（如查计数是否全落 fallback 桶），区分算法问题与环境问题。
「再试一个边界看看」是最典型的额度消耗方式，因为每次都显得成本很低——事前写死「不变体化」才挡得住。
**不因「比失败臂好」而放宽门禁**：拿失败臂当参照系 = 移动球门。

## 3. 否决门：区分「真的解决了冲突」与「换了个包装」

已知某方案「在 A 类有效、在 B 类有害」时，其改进版必须**同时**证明 A 类仍有效 **且**
B 类不再受害。实战：三视图加回近视野后，small 增益几乎不变（+0.0236 vs +0.0239），
cracked 仍负（−0.0196）→ 只是把宽视野换了个包装。若没有否决门，仅看主门为正 +
归因相符，很容易读成「机理成立、只是幅度不够」，下一轮继续投变体。

否决门阈值按**该类的单例敏感度**设（允许恶化不超过 1 个等效实例），
对「信息不在输入里」的类只设不恶化下限，不设改善要求。

## 4. 门禁脚本化 + 回归验证

- 写成 `src/gate_candidate.py`（脚手架在 comp-submit/assets），阈值 / 锚点常数写死在脚本，
  exit code 0 才放行；输出 verdict JSON，每条门带 `why` 字段。
- **用已知线上崩盘的候选做回归验证**：旧判据放行、新门禁拦下，才证明门禁抓住了旧直觉
  抓不到的东西。基线跟自己比 gain=1.5e-08 正确判 fail，证明常数与实际逐位吻合。
- **准入指标对准瓶颈维度**：实战两个候选都是「总 dev mAP 涨、分类损失恶化」，
  其中一个线上 −0.029；门禁改为「`classification_loss` 不得高于锚点」后拦下了另一个。

## 5. 防事前宣布结论

中途轨迹的逐轮差不具预测力，尤其当中间量与最终口径不同（argmax vs TTA + 冻结权重差 +0.026）。
实战在 ep3 外推「需 7 倍加速不可达」，ep4 就反超——基线 ep4 恰是它自己的低谷。
判定必须等终局指标。

## 6. 结论作废与重跑

变更若影响数值（换量化格式、换后端、换后处理），此前所有基于旧数值的结论一律作废重跑，
无论变更方向看起来是好是坏。实战重跑后发现旧结论**低估**了候选（CER 从「未退化」变为「已证实改善」）。
「预期只会更好」不是证据。

修改上游产物（官方模型 / 图）时，做同协议对照并给出数据（三项 CI 全跨零 ⇒ 中性），
如实表述为「解决运行时可用性，不是拿它换质量」。

## 7. 纪律必须配可执行路径

「下载前先预估相关性」与「要算相关性就得先下权重」互相矛盾——纪律没有执行路径时，
真走到那一步只会卡住或被无视。解法是拆两级筛，第一级零成本：

| 级别 | 判据 | 成本 | 作用 |
|---|---|---|---|
| L1 血统预筛 | 训练集 / 团队 / 骨干任一与现役成员同源即淘汰 | 0 | 必要条件，只淘汰不录取 |
| L2 实测相关 | 过 L1 才下权重，算 r < 阈值 | 一次下载 | 充分判定 |

写下任何「先评估再投入」类纪律后，检查评估本身是否需要投入；若矛盾，找一个零成本的必要条件做第一级。

判据还要检查**可自执行性**：每一段指向的动作现在是否真做得了，引用的每个落地物
（基座包、在飞包、门槛清单、标定脚本）是否真实存在。

## 8. 资源阈值也要配执行路径

任何「阈值 / 上限 / 红线」类约束都要回答三个问题：**谁来检测**（常驻守卫还是人工）、
**触发后具体停什么**（指定牺牲顺序，不让内核随机挑）、**善后是什么**
（被停的 run 删干净、日志改名 `.aborted.log`、禁止 resume）。三者缺一，阈值只是个数字。
